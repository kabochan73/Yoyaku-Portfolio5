# 00. プロジェクト概要

フットサルコート1面の予約サイト「FUTSAL PARK」。利用者は空き状況を見て Web で予約し、料金は現地で払う。管理者は予約の確認・電話予約の代理登録と、料金・定休日・臨時休業日の設定を Web で行う。

ゴールは Railway への本番デプロイまで。

## 想定する規模

- コート1面。同時にカレンダーを見ているのは多くて数十人
- 管理者は1人

## スコープ

| 入れる | 入れない |
|---|---|
| 空き状況の閲覧、会員登録・ログイン、予約・キャンセル | オンライン決済（現地払いのみ） |
| マイページ（今後の予約・プロフィール） | 複数コート・複数施設 |
| 管理者による予約の確認・キャンセル・電話予約の代理登録 | パスワードリセット、メール認証、退会 |
| 料金・定休日・臨時休業日の設定、会員検索 | 個人参加、キャンセル待ち、定期予約 |
| 予約・キャンセルのメール通知 | キャンセル料 |

詳細は [01-requirements.md](01-requirements.md)。

## キャッシュの構成

Next.js の Cache Components を使い、トップページを「静的な部分」と「アクセスのたびに描画する部分」に分ける。

| データ | 描画・保存の方法 | 更新のタイミング |
|---|---|---|
| 施設情報（料金・定休日・営業時間など） | 静的な部分（`'use cache'` + `cacheTag('facility')`） | 期限なし。管理者が設定を変えたら再検証する |
| 今週のカレンダー | アクセスのたびにサーバーで描画（`<Suspense>` で後から流し込む） | 常にその時点の最新。古い空き状況は出さない |
| 表示後のカレンダー・ほかの週 | ブラウザで取得 | 60秒ごとに取り直す。API は ETag を返し、変わっていなければ 304 |
| 日ごとの予約・休業日 | Redis | 1分で期限切れ。書き込みがあった日はその場で消す |

予約できるかの最終判定は、常にサーバーが DB を見て行う。画面が古くても二重予約にはならない。

## 実装の順番

層ごとに作る（横切り）。1つの層を、テストまで含めて終えてから次へ進む。

1. 土台: リポジトリ、docker compose、整形・静的解析・テストの設定
2. DB: マイグレーション・制約・シーダー
3. 業務ロジック: モデル、予約のルール、Action、カレンダーの組み立てとキャッシュ
4. API: ルート、FormRequest、Policy、Resource、エラー形式、イベント・メール
5. フロントの土台: API 呼び出し、共通 UI 部品、レイアウト、認証の確認
6. 画面: トップ → ログイン・会員登録 → マイページ → 管理画面
7. CI
8. 本番デプロイと手動確認
